## Conventions Established
- **Supervisor workflow: lead-claude (plan) → implement-codex (code+tests) → review-claude/review-codex (verdict) with verification-based completion markers (e.g. `V1_<X>_REVIEW_COMPLETE`)**: Separates planning, execution, and review responsibilities and produces auditable artifacts in `docs/architecture/` (scope: Every v1 package workflow (core, sessions, surfaces, connectivity, coordination, routing, traits, memory) and harness ports)
- **Per-package layout under `packages/<name>/` as TypeScript-first, isolated, with its own `package.json`, `src/index.ts` re-exports, vitest suite, dist build, and design doc in `packages/<name>/docs/` or `docs/architecture/`**: Allows packages to be runnable and testable in isolation and published independently (scope: All `@agent-assistant/*` packages)
- **Spec-then-implement cycle: author `docs/specs/v1-<area>-spec.md` and `docs/architecture/v1-<area>-implementation-plan.md` before code; reconcile when canonical specs change**: Keeps implementation traceable to spec and supports reconciliation workflows when specs drift (scope: All v1 packages and the v0.5–v0.7 harness improvements)
- **Repair loops: `fix-typecheck` → `fix-tests` → `fix-regressions` → `lead-review` after every impl step**: Tightens 80-to-100 validation; lead-review gates catch regressions before merge (scope: aa-* harness workflows (subagent, planning, scratchpad registries, typecheck/lint))
- **DAG with parallel waves and convergence barriers (e.g. wave1 quiet-hours + signal-inbox, wave2 slack-presence + github-signal)**: Maximizes throughput when slices are independent; barriers ensure build/test stability before next wave (scope: `aa-proactive-signals-master-workflow` and similar multi-slice workflows)
- **Acceptance criterion: skip source edits when broker evidence shows BUILD_EXIT=0 and TEST_EXIT=0**: Avoids speculative churn and respects the deterministic gate contract (scope: Repair-from-evidence steps in Ricky harness workflows)

## Lessons Learned
- Publish workflows must include all packages in the dependency-aware build order, not just the publish matrix (The runtime-core publish matrix included vfs but the build-order step omitted it, so artifact upload failed copying packages/vfs/dist before it existed) - When adding a new package to the publish matrix, also add it to the build-order list and to CI validation; assert dist existence pre-copy
- Marker-based completion can be noisy — prefer verification-based completion with explicit exit codes and signals (Many workflow steps emit STEP_COMPLETE legacy markers mixed with terminal output; later steps switched to verification-based completion (file changes + exit=0)) - For new workflows, drive convergence off verification evidence (file mutations, command exit codes, sentinel strings) rather than printed markers
- Long lead-plan steps can balloon to 60+ minutes of model time (`lead-audit-plan`, `lead-coordination-hardening-plan`, and `lead-plan` runs each took ~1h while implement/review steps stayed under 10m) - Cap planning steps with a tighter prompt or smaller model; planning shouldn't consume more wall clock than implementation
- Reviewers will flag follow-ups even on PASS verdicts — schedule a hardening pass per area (Connectivity, coordination, and post-audit reviews all returned PASS_WITH_FOLLOWUPS that became dedicated `harden-v1-*` workflows) - Bake a hardening slot into the program plan after each implement workflow rather than treating it as ad-hoc
- Renames need a remediation workflow because reviewers find blocking residuals (`rename-relay-assistant-to-agent-assistant-sdk-workflow` (1h37m) was followed by two `remediate-agent-assistant-sdk-rename-workflow` runs) - For repo-wide renames, plan a same-day remediation workflow tied to the review verdict before declaring the rename done
