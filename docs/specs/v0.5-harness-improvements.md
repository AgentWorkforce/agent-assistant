# SPEC: `@agent-assistant/harness` v0.5 / v0.6 / v0.7 Improvements

> **Governing rule:** Separate product identity from execution. Every change must preserve the bounded-turn primitive boundary. The harness is a turn executor, not a runtime; sessions, surfaces, continuation lifecycle, traits, and policy stay in their own packages.

This spec proposes ten prioritized improvements to `@agent-assistant/harness`, scoped to three minor releases (v0.5, v0.6, v0.7). Each item is additive on the public type surface unless explicitly noted; consumer products (sage, nightcto, ricky) MUST compile against the new versions without code changes for any P0/P1 item except where they directly opt in to a new feature.

---

## 1. Release Plan

| Release | Items | Theme |
|---|---|---|
| **v0.5** | 1, 2, 3 | Streaming + cancellation + MCP — minimum viable agentic UX |
| **v0.6** | 4, 5, 6 | Direct provider adapters, parallel tool calls, terminating tools |
| **v0.7** | 7, 8, 9, 10 | Module hygiene, transcript compaction, observability fidelity |

Versioning follows semver-additive: every type change in P0/P1 must be a non-breaking extension of the existing surface in [packages/harness/src/types.ts](packages/harness/src/types.ts:1).

## 2. Improvements

### 2.1 (P0) Streaming on the adapter contract

#### (a) Problem

Today [`ExecutionAdapter`](packages/harness/src/adapter/types.ts:1) only exposes a batch `execute()` returning `Promise<ExecutionResult>`. The harness loop in [runTurn](packages/harness/src/harness.ts:177) emits trace events but does not surface in-flight model output. Both nightcto local-chat and sage Slack threads need to render partial assistant text and tool-call activity as it happens. Trace events ([HarnessTraceEvent](packages/harness/src/types.ts:412)) are an internal observability surface; they are NOT response deltas. Streaming response deltas need a first-class contract distinct from trace.

#### (b) Proposed change

Add an optional `executeStreaming()` method to [`ExecutionAdapter`](packages/harness/src/adapter/types.ts:1), define a new `ExecutionStreamEvent` discriminated union, extend [`ExecutionCapabilities`](packages/harness/src/adapter/types.ts:72) with a `streaming` field, and extend [`ExecutionRequirements`](packages/harness/src/adapter/types.ts:63) so callers can prefer/require/forbid streaming through negotiation.

```typescript
// packages/harness/src/adapter/types.ts (additive)

export interface ExecutionAdapter {
  readonly backendId: string;
  describeCapabilities(): ExecutionCapabilities;
  negotiate(request: ExecutionRequest): ExecutionNegotiation;
  execute(request: ExecutionRequest): Promise<ExecutionResult>;
  executeStreaming?(request: ExecutionRequest): AsyncIterable<ExecutionStreamEvent>;
}

export interface ExecutionCapabilities {
  // ...existing fields...
  streaming: 'none' | 'native' | 'adapter-mediated';
}

export interface ExecutionRequirements {
  // ...existing fields...
  streaming?: 'forbidden' | 'preferred' | 'required';
}

export type ExecutionStreamEvent =
  | { type: 'text_delta'; text: string; index?: number }
  | { type: 'thinking_delta'; text: string }
  | { type: 'tool_call_delta'; callId: string; name?: string; argsDelta: string }
  | { type: 'tool_started'; callId: string; name: string; input: Record<string, unknown> }
  | { type: 'tool_finished'; callId: string; result: ExecutionToolResult }
  | { type: 'tool_failed'; callId: string; error: ExecutionStreamError }
  | { type: 'step_finished'; iteration: number; usage?: ExecutionUsage }
  | { type: 'turn_finished'; result: ExecutionResult }
  | { type: 'error'; error: ExecutionStreamError };

export interface ExecutionStreamError {
  code:
    | 'cancelled'
    | 'timeout'
    | 'backend_execution_error'
    | 'invalid_backend_output'
    | 'tool_bridge_error'
    | 'unsupported_capability'
    | 'other';
  message: string;
  retryable?: boolean;
}
```

Negotiation rules (extend [agent-relay-adapter.ts:negotiateRequest](packages/harness/src/adapter/agent-relay-adapter.ts:135) pattern):

- `requirements.streaming === 'required'` and `capabilities.streaming === 'none'` → `supported: false` with `reason.code: 'other'`, severity `blocking`.
- `requirements.streaming === 'preferred'` and `capabilities.streaming === 'none'` → `degraded: true`, severity `warning`.
- `requirements.streaming === 'forbidden'` is informational; adapter must use `execute()` instead of `executeStreaming()`.

The harness itself gains an internal `runTurnStreaming(input): AsyncIterable<ExecutionStreamEvent>` that wraps [runTurn](packages/harness/src/harness.ts:177). Stream events and trace events MUST co-exist: every `tool_started` stream event has a corresponding `HarnessToolStartedEvent` trace event. Adapters that wrap the harness MUST NOT collapse them.

#### (c) Backwards compatibility

`executeStreaming` is optional (`?`) on `ExecutionAdapter`. The new fields on `ExecutionCapabilities` and `ExecutionRequirements` are likewise optional or default to `'none'` / `undefined`. Existing consumers of [createHarness](packages/harness/src/harness.ts:69) that only call `runTurn` continue to work. The new `runTurnStreaming` is added alongside, not replacing.

#### (d) Conformance test additions

Add to the adapter conformance suite (referenced in [SPEC.md Appendix B](SPEC.md:387)):

1. If `capabilities.streaming !== 'none'`, `executeStreaming()` MUST yield at least one `text_delta` followed by exactly one `turn_finished` for a simple text turn.
2. The `turn_finished.result` MUST equal the result that `execute()` would have returned for the same request (modulo timestamps).
3. Every `tool_started` MUST be followed by exactly one `tool_finished` or `tool_failed` for the same `callId`.
4. After `turn_finished`, the iterable MUST be done (`done: true`).
5. Workers-fetch rule: streaming over HTTP MUST consume the response body or call `body.cancel()` on early termination, per [.claude/rules/workers-fetch.md](.claude/rules/workers-fetch.md:1).

#### (e) Who benefits

- **sage**: Slack/Linear progress visibility. Long agentic specialist runs (`sage/src/swarm/specialist/agentic-specialist.ts`) can stream partial drafts to a thread instead of revealing the whole answer at the end.
- **nightcto**: Streaming is the chat product's baseline UX expectation; required for `packages/local-chat/src/runtime.ts` to feel like every other chat product.
- **ricky**: Stretch — workflow reliability dashboards could surface progress, but requires migration off `@agentworkforce/harness-kit`.
- **msd**: PR reviews take minutes — staring at "Reviewing…" is the worst UX in the product. Streaming powers two surfaces simultaneously: the webapp PR chat pane (token-by-token), and `slack-continuation-delivery` can edit-in-place a Slack message as the review grows. Also enables progress in `pr-concierge` flow.

#### (f) Effort estimate

5–7 engineer-days. Type additions are trivial; the harness-internal stream loop and adapter conformance suite are the bulk.

#### (g) Acceptance criteria

- [ ] `ExecutionStreamEvent` union exported from `@agent-assistant/harness`.
- [ ] `executeStreaming()` implemented on `OpenRouterModelAdapter` (transport-level streaming) and `BuiltInHarnessAdapter` (mediated by harness loop).
- [ ] Cloudflare Workers integration test: streaming via `fetch` ReadableStream end-to-end.
- [ ] Conformance tests (5 above) all pass for at least two adapters.
- [ ] Trace + stream surfaces co-exist: `byoh-local-proof` validation specialist receives both.

### 2.2 (P0) AbortSignal propagation + truthful `cancelled`

#### (a) Problem

[HarnessStopReason](packages/harness/src/types.ts:366) declares `'cancelled'` but nothing in [runTurn](packages/harness/src/harness.ts:177) emits it. There is no public way to abort a turn. Chat UX (nightcto) and Slack-thread UX (sage) both require: user types a new message → previous turn's tool calls and model calls cancel cleanly. Today the only options are `maxElapsedMs` timeout (blunt) or process kill (catastrophic).

#### (b) Proposed change

Thread `AbortSignal` through every input boundary and check it at every iteration boundary AND after each tool call. Adapters mirror the same field on `ExecutionRequest`.

```typescript
// packages/harness/src/types.ts (additive)

export interface HarnessTurnInput {
  // ...existing fields...
  signal?: AbortSignal;
}

export interface HarnessModelInput {
  // ...existing fields...
  signal?: AbortSignal;
}

export interface HarnessToolExecutionContext {
  // ...existing fields...
  signal?: AbortSignal;
}

export interface HarnessApprovalRequestInput {
  // ...existing fields...
  signal?: AbortSignal;
}

// packages/harness/src/adapter/types.ts (additive)
export interface ExecutionRequest {
  // ...existing fields...
  signal?: AbortSignal;
}

export interface ExecutionResult {
  // ...existing fields...
  error?: {
    code:
      | 'unsupported_capability'
      | 'backend_execution_error'
      | 'invalid_backend_output'
      | 'tool_bridge_error'
      | 'timeout'
      | 'budget_exceeded'
      | 'cancelled'              // NEW
      | 'other';
    // ...rest unchanged...
  };
}
```

Harness loop changes in [runTurn](packages/harness/src/harness.ts:177):

1. After [`emit({ type: 'turn_started' })`](packages/harness/src/harness.ts:207) and at the top of every iteration, check `input.signal?.aborted`.
2. After each `await config.model.nextStep(modelInput)` ([harness.ts:238](packages/harness/src/harness.ts:238)), check abort before processing output.
3. After each `await tools.execute(call, context)` ([harness.ts:363](packages/harness/src/harness.ts:363) via `executeToolWithRetry`), check abort.
4. When aborted: build a `HarnessResult` with `outcome: 'failed'`, `stopReason: 'cancelled'`, emit `turn_finished` synchronously, return.

The `signal` MUST be forwarded into model adapters' fetch calls (per [.claude/rules/workers-fetch.md](.claude/rules/workers-fetch.md:1) call-time lambda pattern):

```typescript
// inside any model adapter
const response = await this.fetchImpl(url, { ...init, signal: input.signal });
```

#### (c) Backwards compatibility

`signal` is optional everywhere. Existing callers that never pass a signal see no behavioural change. The `cancelled` stop reason already exists in the enum, so result type narrowing in consumers does not regress.

#### (d) Conformance test additions

1. Aborting before first model call → `outcome: 'failed'`, `stopReason: 'cancelled'`, no model adapter invocation.
2. Aborting mid-tool-call → tool result discarded; loop returns with `cancelled` after current tool completes (we do not interrupt user-supplied registry implementations beyond passing the signal).
3. Aborting between iterations → model adapter NOT called for the next iteration.
4. `ExecutionResult.error.code === 'cancelled'` when adapter receives an aborted signal.
5. After cancellation, the `turn_finished` trace event fires exactly once with the cancelled outcome.

#### (e) Who benefits

- **sage**: Users sending a follow-up Slack message during a long specialist turn cancel the in-flight run instead of waiting it out.
- **nightcto**: Chat UX 101 — user types a new message, abort the previous turn.
- **ricky**: Workflow steps with a deadline can be aborted from the orchestrator without raising `tool_error_unrecoverable`.
- **msd**: A new push to a PR mid-review obsoletes the in-flight review. Today MSD either waits it out or wastes OpenRouter tokens finishing a stale review. AbortSignal lets the dispatcher cancel obsolete reviews on `pull_request.synchronize` webhook events. Direct cost saving on every superseded review.

#### (f) Effort estimate

3–4 engineer-days. Plumbing is mechanical; the careful work is ensuring the abort check is on the right side of every `await` so partial state doesn't leak.

#### (g) Acceptance criteria

- [ ] `signal?: AbortSignal` on `HarnessTurnInput`, `HarnessModelInput`, `HarnessToolExecutionContext`, `HarnessApprovalRequestInput`, `ExecutionRequest`.
- [ ] `'cancelled'` added to `ExecutionResult.error.code` union.
- [ ] [runTurn](packages/harness/src/harness.ts:177) checks abort at every iteration boundary AND after each tool call.
- [ ] `OpenRouterModelAdapter` forwards `signal` to `globalThis.fetch`.
- [ ] Conformance tests above pass against at least two adapters.

### 2.3 (P0) MCP tool support

#### (a) Problem

The Model Context Protocol is the de facto neutral standard for tool registries (Linear MCP, GitHub MCP, filesystem MCP, etc.). Today every product hand-rolls its own [HarnessToolRegistry](packages/harness/src/types.ts:208) — see [packages/harness/src/tools/workspace-tool-registry.ts](packages/harness/src/tools/workspace-tool-registry.ts:1) for the pattern. Adopting MCP unlocks the existing ecosystem instead of forcing every consumer to write adapters.

#### (b) Proposed change

New module under `packages/harness/src/mcp/` exporting:

```typescript
// packages/harness/src/mcp/types.ts (new)

export interface McpServerConfig {
  name: string;
  transport: McpStdioTransport | McpHttpTransport;
  /** Optional allow-list. If unset, all server-provided tools are exposed. */
  allowedToolNames?: string[];
  /** Optional metadata merged into each projected HarnessToolDefinition.metadata. */
  metadata?: Record<string, unknown>;
}

export interface McpStdioTransport {
  kind: 'stdio';
  command: string;
  args?: string[];
  env?: Record<string, string>;
  cwd?: string;
}

export interface McpHttpTransport {
  kind: 'http';
  url: string;
  headers?: Record<string, string>;
  /** Optional fetch impl, MUST be the call-time lambda pattern. */
  fetchImpl?: (input: RequestInfo, init?: RequestInit) => Promise<Response>;
}

export interface CreateMcpToolRegistryOptions {
  servers: McpServerConfig[];
  /** Default `requiresApproval` when MCP server doesn't specify. */
  defaultRequiresApproval?: boolean;
  /** How to label tool name collisions across servers. Default: `${serverName}__${toolName}`. */
  toolNameStrategy?: 'prefix' | 'flat';
}

export function createMcpToolRegistry(
  options: CreateMcpToolRegistryOptions,
): HarnessToolRegistry & McpToolRegistryControl;

export interface McpToolRegistryControl {
  /** Connect (or reconnect) to all configured servers. Idempotent. */
  connect(): Promise<void>;
  /** Disconnect from all servers. Subsequent `execute` calls will fail. */
  disconnect(): Promise<void>;
  /** Server connection statuses for health surfaces. */
  status(): McpServerStatus[];
}

export interface McpServerStatus {
  name: string;
  state: 'disconnected' | 'connecting' | 'connected' | 'failed';
  toolCount?: number;
  lastError?: string;
}
```

[`listAvailable`](packages/harness/src/types.ts:209) projects every connected server's tool list into [`HarnessToolDefinition`](packages/harness/src/types.ts:222). [`execute`](packages/harness/src/types.ts:210) marshals the call through MCP, maps the response to [`HarnessToolResult`](packages/harness/src/types.ts:247). MCP errors map onto [`HarnessToolError`](packages/harness/src/types.ts:258) with `retryable: true` for transport-level failures, `retryable: false` for tool-reported errors.

The HTTP transport MUST use the call-time lambda pattern from [.claude/rules/workers-fetch.md](.claude/rules/workers-fetch.md:1).

The MCP module MUST NOT be re-exported from the default barrel [packages/harness/src/index.ts](packages/harness/src/index.ts:1). Like [the agent-relay subpath](packages/harness/package.json:13), MCP gets its own subpath:

```jsonc
// packages/harness/package.json (additive)
{
  "exports": {
    ".": { /* unchanged */ },
    "./agent-relay": { /* unchanged */ },
    "./mcp": {
      "import": "./dist/mcp/index.js",
      "types": "./dist/mcp/index.d.ts"
    }
  }
}
```

This keeps the worker bundle path (`@agent-assistant/harness`) free of any Node-only deps that the MCP stdio transport may pull in.

#### (c) Backwards compatibility

Net-new module on a new subpath. Zero impact on existing imports.

#### (d) Conformance test additions

1. `createMcpToolRegistry({ servers: [stdioFixture] })` connects, lists ≥1 tool, executes it successfully.
2. HTTP transport survives `vi.stubGlobal('fetch', ...)` test injection (workers-fetch regression test).
3. Tool name collision across two servers resolves via prefix strategy by default.
4. Disconnect mid-turn surfaces `HarnessToolError { retryable: true, code: 'mcp_transport_error' }`.
5. Server-reported tool error (MCP error envelope) maps to `HarnessToolError { retryable: false }` with the original code preserved in `metadata.mcpErrorCode`.
6. `requiresApproval` from server's tool annotations propagates to `HarnessToolDefinition.requiresApproval`.

#### (e) Who benefits

- **sage**: Limited. Sage already has typed `@relayfile/adapter-{github,linear,notion,slack}` projected through `@agent-assistant/specialists` librarians/investigators in [sage/src/swarm/specialist/tool-adapters.ts](../../sage/src/swarm/specialist/tool-adapters.ts:1). Those are the right primary tool surface — typed, Nango-authed, structured. MCP is additive only for community servers without a relayfile counterpart. Do not push sage to migrate.
- **nightcto**: Local-chat users can BYO MCP servers (filesystem, browser, Postgres) without forking the runtime. **Primary beneficiary.**
- **ricky**: Stretch — once ricky migrates from `harness-kit`, MCP gives it a neutral tool surface for workflow steps.
- **msd**: Limited. MSD has its own typed `agent-tool-registry.ts` with Zod schemas for review-specific tools (file reads, finding-aggregation, cross-PR insight injection, convention-extractor). MCP only adds value if MSD wants to expose external community servers (e.g., a Postgres MCP for repo-memory tools). Not a primary win; do not push MSD off the typed registry.

#### (f) Effort estimate

8–12 engineer-days. The MCP SDK integration, transport plumbing, and connection lifecycle are non-trivial. Test fixtures for stdio + HTTP add another day.

#### (g) Acceptance criteria

- [ ] `@agent-assistant/harness/mcp` subpath export available.
- [ ] `createMcpToolRegistry` returns a value implementing `HarnessToolRegistry & McpToolRegistryControl`.
- [ ] Stdio + HTTP transports both pass conformance tests.
- [ ] No additions to the default barrel; worker bundle size unchanged.
- [ ] Documentation example wiring `createMcpToolRegistry` into `createHarness({ tools })`.

### 2.4 (P1) Direct provider adapters (Anthropic, OpenAI, Gemini)

#### (a) Problem

Today the only first-party model adapter is [`OpenRouterModelAdapter`](packages/harness/src/adapter/openrouter-model-adapter.ts:1). OpenRouter adds latency, applies a markup, and obscures provider-specific features (Anthropic prompt caching, OpenAI structured outputs, Gemini grounding). For products where direct provider access matters (nightcto cost, sage caching), we need first-class adapters.

#### (b) Proposed change

Three new files under `packages/harness/src/adapter/`:

- `anthropic-model-adapter.ts` — `AnthropicModelAdapter implements HarnessModelAdapter`
- `openai-model-adapter.ts` — `OpenAIModelAdapter implements HarnessModelAdapter`
- `gemini-model-adapter.ts` — `GeminiModelAdapter implements HarnessModelAdapter`

Each adapter:

1. Uses the call-time lambda pattern: `this.fetchImpl = config.fetchImpl ?? ((input, init) => globalThis.fetch(input, init))`. ([.claude/rules/workers-fetch.md](.claude/rules/workers-fetch.md:1))
2. Always consumes response bodies (read JSON on success, `await response.text()` in error message OR `response.body?.cancel()` before throw).
3. Maps provider error envelopes onto [`HarnessInvalidOutputCode`](packages/harness/src/types.ts:198):

| Provider error class | `HarnessInvalidOutputCode` |
|---|---|
| 401 / invalid api key | `auth_failed` |
| 402 / billing / quota exceeded | `credits_exhausted` |
| 429 / rate limit | `rate_limited` |
| 408 / 504 / abort timeout | `timeout` |
| 400 invalid request | `invalid_request` |
| context length / token limit | `context_length_exceeded` |
| 404 model not found / 400 unknown model | `model_not_found` |
| anything else | `unknown` |

4. Returns [`HarnessModelOutput`](packages/harness/src/types.ts:125) (`final_answer` | `tool_request` | `clarification` | `approval_request` | `refusal` | `invalid`) — never raw provider JSON.

##### Anthropic-specific

- Supports prompt caching via the `cache_control: { type: 'ephemeral' }` annotation on system prompt blocks and the trailing K transcript items (configurable, default 4).
- Supports tool use with the `tools[]` and `tool_choice` request fields.
- Supports native streaming via `stream: true` and SSE parsing — feeds into item 1's `executeStreaming`.
- Documents model selection: `claude-opus-4-7`, `claude-sonnet-4-6`, `claude-haiku-4-5-20251001`.
- Maps `stop_reason: 'refusal'` to `HarnessRefusalOutput`.

##### OpenAI-specific

- Uses the Chat Completions API (NOT the Assistants API — Assistants is a runtime, not a turn executor, and would violate the governing rule).
- Supports `tools` + `tool_choice`, `response_format: { type: 'json_schema' }` for structured output, and `stream: true`.
- Maps the `o1-*` and `o3-*` reasoning models when configured (no streaming for those).

##### Gemini-specific

- Uses `generativelanguage.googleapis.com/v1beta/models/{model}:generateContent` (or `:streamGenerateContent`).
- Supports `tools[]` with `functionDeclarations`. Tool calls emerge as `parts[].functionCall`.
- Maps Gemini safety blocks to `HarnessRefusalOutput` with the safety category in `metadata`.

Each adapter MUST be ≤300 lines. Conformance is verified against [byoh-local-proof](packages/harness/src/adapter/proof) — the validation specialist runs the same canned turn against all three adapters and asserts equivalent `HarnessResult` shape (modulo text content).

```typescript
// shared shape for all three (sketch)
export interface AnthropicModelAdapterConfig {
  apiKey: string;
  model: string;
  maxTokens?: number;
  fetchImpl?: (input: RequestInfo, init?: RequestInit) => Promise<Response>;
  baseUrl?: string;
  cacheTrailingTranscriptItems?: number;
  defaultHeaders?: Record<string, string>;
  now?: () => number;
}
```

#### (c) Backwards compatibility

Net-new files. The existing OpenRouter adapter and its single-shot router variant are unchanged.

#### (d) Conformance test additions

For each adapter, ten tests:

1. Simple text turn → `HarnessFinalAnswerOutput`.
2. Tool-use turn → `HarnessToolRequestOutput` with the right `calls[].name`.
3. Refusal mapped to `HarnessRefusalOutput`.
4. 401 → `HarnessInvalidOutput` with `code: 'auth_failed'`.
5. 429 → `HarnessInvalidOutput` with `code: 'rate_limited'`.
6. Context-length error → `HarnessInvalidOutput` with `code: 'context_length_exceeded'`.
7. Workers-fetch regression: `vi.stubGlobal('fetch', ...)` is honoured.
8. Streaming yields `text_delta` events then `step_finished` (for item 1 integration).
9. AbortSignal aborts in-flight `fetch` (item 2 integration).
10. Response body is consumed on error path (no leaked stream).

Plus the cross-adapter parity test against `byoh-local-proof`.

#### (e) Who benefits

- **sage**: Direct Anthropic adapter unlocks prompt caching across long agentic specialist turns; the cache hit rate on system prompts dramatically reduces input cost. Specialist work currently incurs OpenRouter markup.
- **nightcto**: Reduces cost vs. OpenRouter — important for a chat product where every turn pays the markup.
- **ricky**: Not a near-term beneficiary unless they migrate off `harness-kit`.
- **msd**: **Likely the biggest cost-saving win across all products.** MSD's [dispatcher.ts](../../My-Senior-Dev/app/packages/backend/src/services/msd-assistant/dispatcher.ts) routes every PR review through `createOpenRouterSingleShotAdapter` against Anthropic + OpenAI models — every review pays markup. PR reviews are token-heavy (large diffs, repeated system prompts, multi-agent coordinator+specialist passes). Direct Anthropic adapter with prompt caching attacks both the markup and the repeated-system-prompt cost. MSD has explicit `COST_OPTIMIZATION_TODO.md` and `PER_SEAT_PRICING_ANALYSIS.md` — unit economics matter directly to the business case. Direct OpenAI adapter helps the GPT-4 dev-review and synthesis passes similarly.

#### (f) Effort estimate

10–14 engineer-days total (3–5 per adapter; Anthropic streaming + caching is the heaviest).

#### (g) Acceptance criteria

- [ ] Three adapters under `packages/harness/src/adapter/`, each ≤300 lines.
- [ ] All three pass the per-adapter conformance suite (10 tests each).
- [ ] All three pass the cross-adapter parity test in `byoh-local-proof`.
- [ ] Workers-fetch regression test added per adapter.
- [ ] Streaming integration verified against item 1.
- [ ] Cancellation integration verified against item 2.

### 2.5 (P1) Per-tool `executionMode: 'sequential' | 'parallel'`

#### (a) Problem

The model can return multiple tool calls in a single [`HarnessToolRequestOutput`](packages/harness/src/types.ts:140). Today the harness dispatches them serially in the loop at [harness.ts:358](packages/harness/src/harness.ts:358). For independent reads (e.g. "search Linear AND search GitHub AND read workspace file") this serializes work that should be concurrent. Modern providers happily return parallel tool calls; the harness throws away the parallelism.

#### (b) Proposed change

Add an opt-in execution mode to [`HarnessToolDefinition`](packages/harness/src/types.ts:222):

```typescript
// packages/harness/src/types.ts (additive)

export interface HarnessToolDefinition {
  name: string;
  description: string;
  inputSchema?: Record<string, unknown>;
  requiresApproval?: boolean;
  /**
   * How this tool should be dispatched when present in a multi-call batch.
   * - `sequential` (default): batch is run serially.
   * - `parallel`: this tool may run concurrently with other parallel-mode
   *   tools in the same batch. If ANY tool in the batch is `sequential`,
   *   the entire batch falls back to sequential execution.
   */
  executionMode?: 'sequential' | 'parallel';
  metadata?: Record<string, unknown>;
}
```

In [the tool-call dispatch loop in harness.ts:358](packages/harness/src/harness.ts:358):

1. Inspect `output.calls[].name` and resolve each to its `HarnessToolDefinition`.
2. If every tool in the batch has `executionMode === 'parallel'`, run `Promise.all(calls.map(executeToolWithRetry))`.
3. Otherwise (default), run the batch serially as today.
4. The redundant-tool-loop detector (`recentToolResultHashes` at [harness.ts:411](packages/harness/src/harness.ts:411)) MUST record results in **completion order**, not launch order, when running in parallel. Use `Promise.allSettled` if needed and append signatures as each promise resolves.
5. Emit a new trace event variant `tool_batch_started` once per batch, before any individual `tool_started`:

```typescript
export interface HarnessToolBatchStartedEvent extends HarnessBaseTraceEvent {
  type: 'tool_batch_started';
  mode: 'sequential' | 'parallel';
  callCount: number;
}
```

Add `HarnessToolBatchStartedEvent` to the [`HarnessTraceEvent`](packages/harness/src/types.ts:412) union.

#### (c) Backwards compatibility

`executionMode` is optional; default `sequential` preserves existing behaviour. The new trace event variant is additive on the union — consumers using exhaustive switches need to add a case (deferred to v0.6 release notes; non-exhaustive consumers continue to work).

#### (d) Conformance test additions

1. Batch of two `parallel` tools both running with overlapping latency → wall-clock < sum of latencies.
2. Mixed batch (one `sequential`, one `parallel`) falls back to sequential execution; assert ordering.
3. Redundant-loop detector: parallel tools that all return identical results trip the detector after three identical batches.
4. `tool_batch_started` emitted once per batch with correct `mode` and `callCount`.

### 2.6 (P1) Tool `terminate: true` signal

#### (a) Problem

Some tools are inherently terminating: `submitAnswer(text)`, `escalate(reason)`, `handoff(target)`. After they run, asking the model for "what's next?" wastes a turn and risks the model hallucinating extra content. Today the only way to force termination is for the registry to throw a non-retryable error (which yields `stopReason: 'tool_error_unrecoverable'` — semantically wrong) or for the product to consume the result post-hoc and discard subsequent turns.

#### (b) Proposed change

Add an optional `terminate` field to [`HarnessToolResult`](packages/harness/src/types.ts:247):

```typescript
// packages/harness/src/types.ts (additive)

export interface HarnessToolResult {
  callId: string;
  toolName: string;
  status: 'success' | 'error';
  output?: string;
  structuredOutput?: Record<string, unknown>;
  error?: HarnessToolError;
  usage?: HarnessUsage;
  /**
   * When `true`, the harness treats this tool result as the terminal step:
   * after the current batch completes, it synthesizes a `final_answer` from
   * the result's text payload and stops with `stopReason: 'answer_finalized'`.
   *
   * If multiple results in the same batch set `terminate: true`, the harness
   * concatenates their text payloads in completion order (consistent with the
   * batch's executionMode rules in §2.5). If `terminate` is true on at least
   * one result but ANY result in the batch has `terminate !== true`, the
   * harness ignores the signal and continues normally — terminating tools
   * are an all-or-nothing batch contract.
   */
  terminate?: boolean;
  metadata?: Record<string, unknown>;
}
```

Harness behaviour after a batch resolves:

1. If `every(r => r.terminate === true)`:
   - Synthesize `text` from `result.output ?? result.structuredOutput?.text ?? result.structuredOutput?.message ?? ''`. (If no usable text, treat as empty answer.)
   - Push a synthetic `HarnessAssistantThoughtStep { outputType: 'final_answer', text }` onto the transcript.
   - Build a `HarnessResult` with `outcome: 'completed'`, `stopReason: 'answer_finalized'`, `assistantMessage: { text }`.
   - Return without another model round-trip.
2. Otherwise: proceed normally.

#### (c) Backwards compatibility

`terminate` is optional. Tools that don't set it behave exactly as before.

#### (d) Conformance test additions

1. Single tool returning `{ terminate: true, output: 'done' }` → `HarnessResult.outcome === 'completed'`, `stopReason === 'answer_finalized'`, `assistantMessage.text === 'done'`, `state.modelCalls.length === 1` (no extra model round-trip).
2. Two tools in a parallel batch, both with `terminate: true` → text is concatenated in completion order.
3. Mixed batch where one tool sets `terminate: true` and another doesn't → harness ignores the signal, continues normally.
4. `terminate: true` on a tool that errored out → ignored (terminate only applies to `status: 'success'`).
5. `terminate: true` with no usable text → still terminates, with empty `assistantMessage.text`.

#### (e) Who benefits

- **sage**: Specialists ending in a `submitFindings` tool stop cleanly without a wasted model round-trip per finding.
- **nightcto**: Less relevant; chat turns typically end on `final_answer` from the model directly.
- **ricky**: Workflow handoff tools (`handoff`, `escalate`) can terminate the harness turn deterministically.
- **msd**: MSD's coordinator-agent → synthesis pipeline likely calls a `submitFindings` / `synthesizeReview` tool at end of agentic-specialist passes. `terminate: true` skips a wasted final model round-trip per pass — small per-call but multiplied across coordinator + N specialists per PR review.

#### (f) Effort estimate

2 engineer-days.

#### (g) Acceptance criteria

- [ ] `terminate?: boolean` on `HarnessToolResult`.
- [ ] Post-batch handling implemented in [harness.ts:442](packages/harness/src/harness.ts:442) before the `continue` that returns to the model.
- [ ] Conformance tests above pass.
- [ ] Documentation example with `submitAnswer` tool.

### 2.8 (P2) `transformTranscript` hook for compaction

#### (a) Problem

Long agentic specialist turns hit context-window limits. The transcript that the model sees ([harness.ts:228](packages/harness/src/harness.ts:228) builds the model input from `state.transcript`) grows monotonically across iterations. Today the only options are blunt: lower `maxIterations`, drop tool results, or manually compact upstream. There is no in-loop hook to summarize or trim the transcript that the model receives without losing it from `state.transcript` (which is needed for `HarnessResult` and emit).

#### (b) Proposed change

Add an optional hook to [`HarnessHooks`](packages/harness/src/types.ts:512):

```typescript
// packages/harness/src/types.ts (additive)

export interface HarnessHooks {
  clarifyOnToolResult?: HarnessToolEvidenceClarificationHook;
  onInvalidModelOutput?: (
    output: HarnessInvalidOutput,
    state: HarnessExecutionState,
  ) => Promise<void> | void;
  onToolError?: (
    result: HarnessToolResult,
    state: HarnessExecutionState,
  ) => Promise<void> | void;
  onTurnFinished?: (
    result: HarnessResult,
    state: HarnessExecutionState,
  ) => Promise<void> | void;
  /**
   * Called immediately before the harness builds `HarnessModelInput` from
   * `state.transcript`. The returned transcript is what the model will see
   * for THIS iteration only. `state.transcript` (used by emit and the final
   * HarnessResult) is unchanged.
   *
   * Useful for compacting older steps when the cumulative transcript would
   * exceed the model's context window. The hook MUST preserve transcript
   * shape: every returned item must satisfy HarnessTranscriptItem.
   */
  transformTranscript?: (
    transcript: HarnessTranscriptItem[],
    state: HarnessExecutionState,
  ) => HarnessTranscriptItem[] | Promise<HarnessTranscriptItem[]>;
}
```

Implementation in [harness.ts:217](packages/harness/src/harness.ts:217), right before constructing `HarnessModelInput`:

```typescript
const visibleTranscript = config.hooks?.transformTranscript
  ? await config.hooks.transformTranscript(
      [...state.transcript],
      executionState(input, state, startedAt, config),
    )
  : [...state.transcript];

const modelInput: HarnessModelInput = {
  // ...existing fields...
  transcript: visibleTranscript,
  // ...rest unchanged...
};
```

The hook MUST NOT mutate `state.transcript`; the harness defensively passes a copy. If the hook throws, the harness falls back to the untransformed transcript and emits a warning via `console.warn`.

#### (c) Backwards compatibility

Optional hook. Existing consumers see no change.

#### (d) Conformance test additions

1. Hook returning a strict subset of the transcript → model adapter receives the subset; `state.transcript` (and `HarnessResult.traceSummary`) is unchanged.
2. Hook returning a synthesized "compaction summary" item → model adapter sees it; downstream emit still receives the original transcript.
3. Hook throws → harness falls back to untransformed transcript; warning logged; turn completes successfully.
4. Async hook is `await`ed before model adapter is invoked.
5. Hook receives the transcript that includes the most recent tool result (i.e. it's called AFTER tool dispatch, before the next model call).

#### (e) Who benefits

- **sage**: Long agentic specialist turns hitting Claude context limits can in-loop summarize tool result steps older than N iterations.
- **nightcto**: Long chat threads with rich tool history — local-chat can drop verbose tool outputs from older iterations.
- **ricky**: Workflow steps with high tool-result volume can compact in-flight.
- **msd**: Big PRs (50+ file diffs) accumulate substantial tool-result bloat across coordinator + per-file specialist passes. Without in-loop compaction, MSD has to either truncate up front (lose context) or hit context limits mid-review (truncated review = bad review). `transformTranscript` lets MSD compact older per-file readings while keeping recent findings hot.

#### (f) Effort estimate

2 engineer-days.

#### (g) Acceptance criteria

- [ ] `transformTranscript` field on `HarnessHooks`.
- [ ] [harness.ts:217](packages/harness/src/harness.ts:217) call site invokes the hook before building `HarnessModelInput`.
- [ ] `state.transcript` is unchanged by the hook.
- [ ] Conformance tests above pass.

### 2.10 (P2) Trace settlement semantics

#### (a) Problem

Today [`config.trace.emit`](packages/harness/src/types.ts:408) returns `Promise<void> | void` and the harness `await`s every emit call ([harness.ts:899](packages/harness/src/harness.ts:899)). However:

1. There is no documented contract that registered async listeners are fully `await`ed before `runTurn` resolves.
2. The `emitFinishedSafely` swallow of trace failures ([harness.ts:954](packages/harness/src/harness.ts:954)) is correct for resilience but does not give async sinks (e.g. Cloudflare Workers `waitUntil`) a chance to flush deferred work.
3. Consumers using a fan-out trace sink with `Promise.all` listeners cannot reliably know when all listeners settled.

#### (b) Proposed change

1. Document and enforce: every `config.trace.emit` invocation is `await`ed in order — the harness already does this, but the contract was implicit. Add a docblock to [`HarnessTraceSink`](packages/harness/src/types.ts:408):

```typescript
/**
 * Trace sink for harness execution events.
 *
 * Settlement contract: the harness awaits every `emit()` call in order. The
 * `turn_finished` event is the last emit; runTurn does not resolve until
 * `emit({ type: 'turn_finished' })` has settled.
 *
 * If `flush()` is implemented, runTurn awaits it after the final emit. This
 * is the hook for async sinks (Cloudflare Workers waitUntil, batched HTTP
 * shippers) to drain deferred work before the turn promise resolves.
 *
 * Trace sink failures are swallowed — runtime correctness takes precedence
 * over observability.
 */
export interface HarnessTraceSink {
  emit(event: HarnessTraceEvent): Promise<void> | void;
  flush?(): Promise<void> | void;
}
```

2. Implement `flush` invocation at the end of [`emitFinishedSafely`](packages/harness/src/harness.ts:926):

```typescript
async function emitFinishedSafely(
  config: NormalizedConfig,
  input: HarnessTurnInput,
  state: MutableState,
  result: HarnessResult,
): Promise<void> {
  try {
    if (!config.trace) return;
    await config.trace.emit({ type: 'turn_finished', /* ... */ });
    state.finalEventType = 'turn_finished';
    result.traceSummary.finalEventType = 'turn_finished';
    if (typeof config.trace.flush === 'function') {
      await config.trace.flush();
    }
  } catch {
    // swallow — runtime result survives trace sink failures
  }
}
```

#### (c) Backwards compatibility

`flush` is optional. Existing sinks see no change.

#### (d) Conformance test additions

1. Register a sink whose `emit` returns a deferred promise. Assert `runTurn` does not resolve before all `emit` promises settle.
2. Register a sink with both `emit` and `flush`. Assert `flush` is called exactly once, after `turn_finished`, and `runTurn` does not resolve until `flush` settles.
3. `flush` throws → swallowed; `runTurn` resolves successfully.
4. `emit` rejects mid-turn → swallowed; subsequent emits and `flush` still fire.
5. Cloudflare Workers integration test: a `waitUntil`-backed sink completes its background work before the worker response is dispatched.

#### (e) Who benefits

- **sage**: Workers `waitUntil`-style trace shippers (e.g. uploading every event to a logging endpoint) drain reliably before the worker terminates.
- **nightcto**: Local-chat trace sinks that batch to disk or HTTP can flush before the turn promise resolves.
- **ricky**: Workflow step traces are ordered and durable.
- **msd**: MSD's `@agent-assistant/telemetry` + `agent-trajectories` integration depends on traces draining before a review turn resolves. Combined with `slack-continuation-delivery`, settlement semantics mean the Slack message and the trajectory record are never out-of-order. Today this works in practice but isn't guaranteed by contract.

#### (f) Effort estimate

1 engineer-day.

#### (g) Acceptance criteria

- [ ] `flush?(): Promise<void> | void` on `HarnessTraceSink`.
- [ ] [emitFinishedSafely](packages/harness/src/harness.ts:926) calls `flush()` when present.
- [ ] Settlement contract documented in the type docblock.
- [ ] Conformance tests above pass.

## 5. Open Questions

1. **`executeStreaming` vs. `execute` — coexist or supersede?** Current proposal has them coexist; `execute` is the batch primitive, `executeStreaming` is opt-in. Should the harness internally implement `execute` in terms of `executeStreaming + drain`, or keep them as parallel code paths? Decision affects implementation effort by ~3 days.

2. **MCP server lifecycle ownership.** Does `createMcpToolRegistry` own the server connection (spawn stdio process, manage reconnect), or does it accept an already-connected client? Spawning is more user-friendly but couples the harness to a specific MCP SDK and lifecycle model.

3. **AbortSignal semantics inside long-running tools.** The harness checks abort BEFORE and AFTER each tool call, but cannot interrupt a user-supplied registry's `execute` mid-call. Do we document this limitation, or do we mandate that registries wire `signal` through and respect it (impossible to enforce)? Current proposal: document, don't mandate.

4. **Direct provider adapter scope.** Three adapters is a lot. Should v0.6 ship with just Anthropic (sage's biggest win) and defer OpenAI + Gemini to v0.7 or v0.8? Trade-off: faster v0.6 release vs. broader provider coverage.

5. **Subpath migration aggressiveness.** Is a one-minor-version deprecation window (v0.7 warns, v0.8 removes) enough? Some consumers lag; we may need two-minor-version windows. Alternatively, keep root re-exports indefinitely and accept the bundle bloat for compatibility.

6. **`terminate: true` and tool errors.** Current proposal: `terminate` is ignored if `status === 'error'`. Should an errored tool ever be allowed to terminate the turn (e.g. `escalate` tool that errors but still wants to short-circuit)? If yes, semantics get murky — what's the assistant message? Open for owner decision.

## 6. Out of Scope

- **Vector-embedding memory** — belongs in `@agent-assistant/memory`, not harness. Following the jcode pattern: memory is a turn-context enrichment source, not a runtime concern. The harness consumes the assembled context, it does not retrieve memories.
- **Sandbox abstraction** — belongs in `@agent-assistant/vfs`. Following the flue pattern: sandboxing is a tool-execution concern that the registry encapsulates; the harness sees only `HarnessToolResult`.
- **Durable workflows / hibernation resume** — belongs in `@agent-assistant/continuation` or product runtime. Following the open-agents pattern: the harness emits structured continuation payloads ([HarnessContinuation](packages/harness/src/types.ts:291)), but the persistence + resume lifecycle is a product concern. Adding hibernation here would re-open the "harness is a runtime" trap that the governing rule forbids.
- **Steering / mid-turn message injection** — belongs in `@agent-assistant/sessions` or `core`, not the harness. Following the pi-mono pattern: a turn is bounded by definition. Mid-turn steering is a session-level concern that should manifest as a fresh turn, not as an in-loop interrupt.
